# Alexios local V3 — execução por turno e múltiplos locutores

> **Branch experimental.** A V2 (`python continuous.py`) permanece intacta.
> A V3 exige que o `alexios-web` implemente os endpoints `/v3/agent/*`
> antes de estabelecer uma sessão real. Não aponte para produção esperando que
> `/v3/agent/sync` funcione antes do deploy do servidor V3.

## Contrato de arquitetura

Uma **instância** contém todos os locutores. O dispositivo mantém embeddings
temporários de vozes (`speaker_01`, `speaker_02`, ...) para identificar
autores dos turnos; **não** mantém contexto semântico por locutor. O servidor
organiza um único contexto por `instanceId`.

- `turn_end`: fim semântico detectado pelo Smart Turn. Sempre atualiza
  contexto/postura no servidor, mas **nunca** autoriza resposta falada.
- `turn_chunk`: transcrição de um segmento parcial quando a fala é longa,
  **sem** declarar o fim do turno.
- `floor_open`: uma única autorização para o servidor avaliar se deve
  responder após silêncio confirmado; a IA pode escolher silêncio.
- `speech_started`: sinal de prioridade para invalidar imediatamente
  oportunidades de resposta abertas anteriormente; não executa IA.
- O `poll` V2 ainda mantém a presença e recebe comandos ON/OFF.

O `EventDispatcher` envia `turn_end`, `turn_chunk` e `floor_open`
serialmente por instância; um `floor_open` nunca ultrapassa uma transcrição
ainda processando no Whisper. `speech_started` usa um canal prioritário,
independente da fila de transcrição, com `activityEpoch` crescente.
O **backend** deve validar `activityEpoch` e a lease *na transação de
publicação da resposta* para descartar resultados atrasados.

## Requisitos

- Python 3.12 e sistema operacional **64 bits ARM64** no Raspberry Pi 4;
  Ubuntu Linux x86_64 também permite desenvolvimento.
- Microfone compatível com PortAudio/`sounddevice`.
- Repositórios de modelos open-source existentes; **nenhum fine-tuning**.
- Modelos locais baixados apenas ao executar o instalador.
- Memória livre suficiente para Silero, Smart Turn, CAM++ e Whisper tiny;
  nenhum benchmark específico no Pi 4 foi concluído ainda.

Instalação:

```bash
git fetch origin
git switch feature/turn-aware-multispeaker-v3
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-v3.txt
python scripts/download_v3_models.py
cp .env.example .env  # se ainda não existir
```

Use o mesmo `ALEXIOS_INSTANCE_ID` e `ALEXIOS_AGENT_TOKEN` já utilizados na
V2, sem revelar seus valores. Para testar o protocolo **antes da produção**,
use `ALEXIOS_BRIDGE_URL` apontando a um servidor V3 próprio.

```bash
python continuous_v3.py --list-devices
python continuous_v3.py --device 10 --model tiny --model-threads 1
```

Se o servidor ainda não possuir `/v3/agent/sync`, a V3 finaliza
explicitamente **antes** de ligar o microfone. Use `continuous.py` nesse caso.

## Pesos e licenças

O script `scripts/download_v3_models.py` utiliza fontes oficiais:

- Silero: distribuição `silero_vad.onnx` do projeto sherpa-onnx
- Smart Turn: `pipecat-ai/smart-turn-v3/smart-turn-v3.2-cpu.onnx`, ONNX 8,68 MB,
  SHA-256 verificado durante download, licença BSD-2-Clause
- CAM++: `3dspeaker_speech_campplus_sv_zh-cn_16k-common.onnx` distribuído
  pelo sherpa-onnx; verificar termos de uso da distribuição do modelo

O script não versiona modelos nem salva embeddings de locutores em disco.
`models/v3/` deve permanecer no `.gitignore`. Os embeddings são guardados
apenas em RAM durante a execução atual e os locutores são identificados por
IDs pseudônimos. Dois falantes simultâneos ou um trecho muito curto podem
resultar em `speaker_unknown` ou atribuição ao locutor dominante; a V3 inicial
não implementa separação robusta de fontes.

## Requisitos para o servidor V3

O contrato de integração necessário no `alexios-web` é:

| HTTP | Corpo | Resposta de sucesso |
|---|---|---|
| POST `/v3/agent/sync` | `instanceId`, `runId` | `{ "nextSequence": 1 }` |
| POST `/v3/agent/turn` | identidade + `eventId`, `sequence`, `turnId`, `speakerId`, `transcript`, timestamps, `activityEpoch` | `{ "accepted": true }` |
| POST `/v3/agent/chunk` | mesmo contrato de turno, sem conclusão | `{ "accepted": true }` |
| POST `/v3/agent/floor` | identidade + `eventId`, `sequence`, `afterSequence`, `activityEpoch`, `silenceMs` | `{ "accepted": true }` |
| POST `/v3/agent/activity` | identidade + `state: "speech_started"`, `activityEpoch` | `{ "accepted": true }` |

Todos os endpoints usam `Authorization: Bearer ALEXIOS_AGENT_TOKEN`.
O servidor **deve** entregar idempotência por `eventId`, impor sequência
monótona por instância, aceitar reenvio da mesma sequência, rejeitar `floor_open`
obsoleto e impedir `speech` em `turn_end` por código, não só prompt.
`/v3/agent/sync` deve reconciliar a sequência após reinicialização.

## Segurança operacional e limitações de início

- Nenhum áudio cru é enviado à web. O Python manda apenas texto transcrito,
  identificador de locutor e metadados temporais.
- A fila de eventos em RAM é limitada. Se ficar cheia, a captação é
  interrompida em vez de descartar áudio silenciosamente.
- **Ainda não há spool durável** de turnos no disco. Se houver falha completa
  do processo após uma transcrição e antes da confirmação HTTP, esse evento
  pode ser perdido. Persistência e reconciliação no servidor são a próxima
  etapa de confiabilidade.
- A conexão interrompida por mais de 35s suspende o microfone (mesmo critério
  da V2). Transcrições já concluídas permanecem na fila em RAM enquanto o
  processo estiver ativo.
- Cada detecção de voz invalida a oportunidade de fala anterior. O servidor
  precisa confirmar o fechamento antes de publicar uma resposta.
- Sem hardwares/modelos reais, os testes executados são unitários com mocks:
  **não** garantem latência de ponta a ponta no Pi 4.

## Identificação robusta de locutores — experimento

O CAM++ agora recebe **somente os frames que o Silero VAD marcou como fala**.
O áudio original do turno continua sendo entregue sem cortes ao Whisper para
preservar o reconhecimento de palavras. O buffer específico de identificação
é limitado aos **últimos 8 segundos de voz detectada**, não aos últimos 8
segundos da gravação incluindo silêncio.

Para prevenir identidades falsas, `CamPlusRegistry.identify` aplica:

1. Qualidade mínima: >=0,8s de voz (não duração total do turno), nível RMS
   adequado, sem clipping excessivo e embedding numérico válido.
2. Comparação por CAM++ com limiar `0.6` (configurável). Amostras próximas de
   uma identidade existente, mas abaixo do limiar, ficam `speaker_unknown`
   em vez de cadastrar outro ID.
3. Cadastro inicial apenas com >=1,8s de voz. **Após existir um locutor**,
   uma voz claramente diferente pode ganhar um ID na primeira amostra de
   qualidade (similaridade máxima de 0,20, hipótese conservadora).
   Vozes menos distintas precisam de duas amostras consistentes em até três
   minutos; a fala intercalada de outra pessoa não apaga o candidato.
4. Galeria efêmera de até três embeddings por pessoa: novas referências só
   são aceitas após reconhecimento de alta confiança. Uma referência
   alternativa pode recuperar a voz, com margem conservadora entre candidatos.
5. Nenhum embedding é gravado no disco, enviado à web ou incluído nos logs.
   `--debug-audio` expõe apenas dados estruturais (motivo, duração, score).

Estes valores são **hipóteses de calibração**, não thresholds cientificamente
ótimos para o microfone, sala e sotaques utilizados. `speaker_unknown` pode
aumentar: é preferível a inventar outro `speaker_XX` em fala curta.

### Parâmetros locais

```bash
python continuous_v3.py --model tiny --device 10 --debug-audio \
  --speaker-threshold 0.6 \
  --speaker-min-voice-seconds 0.8 \
  --speaker-min-enroll-seconds 1.8 \
  --speaker-near-margin 0.07 \
  --speaker-distinct-max-similarity 0.20
```

### Identidade estável na alternância de pessoas

O registro permanece em memória durante a execução Python; não é
reiniciado a cada turno. Sequência pretendida:

```text
Pessoa A → speaker_01
Pessoa B → speaker_02
Pessoa A → speaker_01
Pessoa B → speaker_02
```

O CAM++ tenta recuperar sempre um ID já cadastrado antes de considerar
uma voz nova. Se a gravação for curta ou ambígua, pode retornar
`speaker_unknown`: não deve criar `speaker_03` por engano. A primeira
gravação de B só recebe `speaker_02` imediatamente se tiver voz útil e
similaridade suficientemente baixa com A. Nos demais casos, B deverá
fornecer mais evidências para confirmação. Esses limites ainda exigem
calibração com gravações reais para medir falsas divisões e falsas
associações.

### Avaliação reprodutível sem rede

Reunir gravações PCM16 mono a 16k de **pelo menos três pessoas**, com
consentimento, duas ou mais gravações por locutor. Incluir falas curtas
(`Alô?`), frases com 2–5s de voz, mudanças de volume/distância e ruído.
Exemplo de manifesto `samples/manifest.json`:

```json
[
  {"wav":"a-01.wav","speaker":"pessoa_a"},
  {"wav":"b-01.wav","speaker":"pessoa_b"},
  {"wav":"a-02.wav","speaker":"pessoa_a"},
  {"wav":"b-02.wav","speaker":"pessoa_b"}
]
```

```bash
python scripts/evaluate_speakers_v3.py --manifest samples/manifest.json
```

O avaliador fornece `fragmentation_extra_ids` (quantos IDs extras foram
atribuídos à mesma pessoa), `false_merge_extra_people` (quantas pessoas
compartilharam IDs), taxa `speaker_unknown`, e latências p50/p95.
**Os resultados reais ainda precisam ser medidos** no dispositivo de destino;
os testes unitários usam simuladores, sem ONNX real.

Comparar *a mesma ordem* de gravações na versão anterior e nesta branch.
Não aprovar redução de fragmentação se ela elevar falsos agrupamentos.
A identificação de locutor não equivale a autenticação biométrica.

### Base técnica e limitações

- API oficial de embedding/manager: https://k2-fsa.github.io/sherpa/onnx/speaker-identification/
- Busca com limiar, cadastro de várias amostras e interpretação dos scores:
  https://k2-fsa.github.io/sherpa/onnx/c-api/html/classsherpa__onnx_1_1cxx_1_1SpeakerEmbeddingManager.html
- Evidências sobre limitações de falas curtas:
  https://ieeexplore.ieee.org/abstract/document/11464059

Não trocar o CAM++ nem o Whisper automaticamente sem benchmark. O CAM++ não
separa vozes simultâneas; ambientes com sobreposição requerem outro modelo de
segmentação/diarização. A qualidade de transcrição ficará para uma etapa
opcional após a validação desta melhoria.

## Diagnóstico quando há silêncio no terminal ou não aparecem respostas

A V3 registra transições `[V3]`, etapas `[WHISPER]` e confirmação
`[HTTP V3]`. Para inspecionar cada bloco de sinal e decisão do modelo:

```bash
python continuous_v3.py --list-devices
python continuous_v3.py --mic-test 5 --device 10
python -u continuous_v3.py --model tiny --model-threads 1 --device 10 --debug-audio
```

Substitua `10` pelo dispositivo de **entrada** correto. Sem `--device`,
o sistema usa o microfone padrão, que pode estar errado em Linux.
`--mic-test` não carrega modelos, não consulta o servidor e não envia áudio.
Leia os valores `rms` e `pico` enquanto fala e durante o silêncio.

- `[AUDIO] rms=0.0000 pico=0.0000`: dispositivo errado, silenciado ou
  sinal baixo. Consulte `--list-devices`, ALSA/PulseAudio/PipeWire.
- `[AUDIO] ... vad=silencio` apesar de picos perceptíveis: verificar
  threshold Silero, ruído e amostragem de 16k.
- `[SILERO] fala detectada`: o modelo encontrou atividade vocal.
- `[SMART TURN] pausa=... turno_completo=...`: decisão semântica.
- `[V3] turn_end`: áudio finalizado e encaminhado para transcrição.
- `[WHISPER] transcrição vazia`: nada será enviado como turno.
- `[HTTP V3] turn_end confirmado`: envio persistido na web.
- `[HTTP V3] floor_open confirmado`: abriu oportunidade de resposta;
  o servidor ainda pode decidir não falar ou invalidá-la por nova voz.

O `sherpa-onnx` guardava originalmente até 100 segundos de fala num buffer
de 3 segundos, causando `circular-buffer.cc:Push: Overflow!`. Agora o
VAD usa até 45s como limite de referência e reserva 120s de buffer.
Esse aviso indica expansão da capacidade pelo próprio sherpa-onnx;
**não comprova perda de amostras nem um crash**.

Para evitar respostas após ruído de fundo, `floor_open` só segue a
confirmação HTTP de pelo menos um `turn_end` com texto no epoch vigente.
A fila de eventos continua serializada por instância, e não por speaker.
